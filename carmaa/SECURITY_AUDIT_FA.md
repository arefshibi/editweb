# گزارش ممیزی امنیتی CarMaa — نسخهٔ تحویلی

**دامنهٔ بررسی:** فایل‌های موجود در بستهٔ فرانت‌اند و سورس بک‌اند اضافه‌شده در همین خروجی. این گزارش ممیزی کد/تست محلی است، نه گواهی امنیت یا گزارش نفوذ زنده.

## خلاصهٔ یافته‌های نسخهٔ قبلی و تغییرات انجام‌شده

| یافته در نسخهٔ قبلی | ریسک | وضعیت در خروجی فعلی |
|---|---|---|
| کد ورود ثابت `123456` در جاوااسکریپت | ورود جعلی و تصاحب حساب نمایشی | مسیر ثابت حذف شد؛ OTP باید از API و پیامک واقعی تأیید شود. |
| ذخیره/اعتماد به حساب کاربر در مرورگر به‌جای نشست server-side | دستکاری هویت سمت کلاینت | مسیر احراز هویت تغییر یافته تا از کوکی `HttpOnly` و session digest سمت سرور استفاده کند؛ بخش‌هایی از مدل دادهٔ قدیمی هنوز محلی هستند. |
| پنل `admin.html` تصمیم‌گیری مبتنی بر مرورگر | دسترسی مدیریتی بدون نقش معتبر | پنل جدید ابتدا `/auth/me` را بررسی و role را سمت سرور چک می‌کند؛ API مدیریت هم از middleware نقش استفاده می‌کند. |
| پرداخت نمایشی که بعد از زمان کوتاه موفق برمی‌گشت | ارتقای آگهی بدون پرداخت واقعی | موفقیت سمت کلاینت حذف شده؛ callback باید سمت سرور با زرین‌پال verify شود. آگهی موجود در DB لازم است. |
| داده‌های آگهی و قابلیت‌های متعدد در `localStorage` | ناسازگاری چند کاربر/دستکاری داده و نبود مرز اعتماد | API و schema برای بخش‌های اصلی ساخته شده‌اند، اما تمام UI قدیمی هنوز به backend مهاجرت نکرده؛ این مانع انتشار عمومی کامل است. |

## کنترل‌های اضافه‌شده

- PostgreSQL با محدودیت‌ها و indexهای داده، Redis برای rate limit مشترک؛ در production نبود Redis باعث رد درخواست حساس می‌شود.
- OTP شش‌رقمی با عمر پنج دقیقه، ذخیرهٔ digest مبتنی بر pepper، حداکثر تلاش، انقضای یک‌بارمصرف، cooldown، حد درخواست IP و شماره؛ درخواست‌های موازی هر شماره در دیتابیس سریال می‌شوند.
- نشست تصادفی با digest سمت سرور، کوکی `HttpOnly`, `SameSite=Strict`, `Secure` در production، logout/revocation و کنترل role.
- کنترل Origin و CORS محدود، Helmet، محدودیت اندازهٔ بدنه، timeout پرس‌وجو و پاسخ خطای عمومی.
- بررسی مالکیت/عضویت در عملیات حساس، فیلدهای API با schema allow-list و queryهای SQL پارامتری.
- پیام‌رسانی فقط برای طرف‌های گفتگو، block دوطرفه، محدودیت نرخ، و گزارش تخلف از endpoint اعتبارسنجی‌شده. عملیات نوشتنی حساسِ علاقه‌مندی/دنبال‌کردن/مسدودسازی/پذیرش پاسخ نیز rate limit دارند.
- پرداخت مبتنی بر کاتالوگ قیمت سرور، idempotency key، تأیید مبلغ و authority با provider و فعال‌سازی در تراکنش با row lock.
- آپلود تصویر با محدودیت اندازه/ابعاد، بررسی MIME واقعی، بازپردازش به WebP و نام تصادفیِ تولیدشده از سرور؛ آواتار باید به رکورد تصویر متعلق به همان کاربر اشاره کند.
- پنل مدیریت مبتنی بر نقش و ثبت عملیات حساس در جدول audit؛ هیچ مدیر پیش‌فرضی وجود ندارد.

## آزمون‌های انجام‌شده در این محیط

- `npm test`: **۲۵ تست محلی از ۲۵ تست موفق** (واحد، بررسی قرارداد سورس و یک آزمون VM برای DTO فرانت‌اند).
- `npm run check`، `node --check` برای فایل‌های `js/*.js` و `bash -n backend/test/staging-smoke.sh`: موفق.
- بررسی ایستا برای مسیر OTP ثابت، توکن ذخیره‌شده در localStorage، ارتقای پولی از سمت کلاینت و جریان تأیید پرداخت.

## یافته‌های جدید در این دور

- تراکنش migration اولیه: دستورهای `BEGIN` و `COMMIT` داخلی از `001_initial.sql` حذف شدند تا اجرایندهٔ migration تمام ساخت schema و ثبت `schema_migrations` را در یک تراکنش واحد انجام دهد؛ regression test اضافه شد. Migration روی PostgreSQL واقعی اجرا نشده است.
- تأیید نمایشی آگهی: تایمرِ انتشار خودکار کلاینت در حالت `CARMA_API.enabled` غیرفعال است؛ تصمیم moderation باید از سرور بیاید.
- حریم خصوصی: دلیل رد آگهی از query عمومی حذف و تنها در query کاربرِ مالک باقی مانده است؛ آگهی منقضی از فهرست عمومی حذف می‌شود.
- آگهی/عکس: اطلاعات تکمیلی با schema strict ذخیره می‌شود، عکس باید متعلق به کاربر باشد و URL تصویر با scheme فعال/HTTP از DTO رد می‌شود. این تضمین جایگزین بررسی تمام sinkهای HTML در کل legacy frontend نیست.
- اسکریپت `backend/test/staging-smoke.sh` اضافه شده است؛ فقط‌خواندنی و محافظت‌شده در برابر target راه دور است؛ در این محیط اجرا نشده است.

## آزمون‌هایی که هنوز انجام نشده‌اند

در محیط تولید فایل، `npm install` با timeout مواجه شد و Docker/PostgreSQL/Redis اجرایی در دسترس نبودند؛ در نتیجه موارد زیر را نمی‌توانم موفق اعلام کنم:

- تست routeها در برابر PostgreSQL و Redis واقعی، migration و رقابت هم‌زمان چند درخواست.
- تست پیامک با حساب واقعی کاوه‌نگار و callback پرداخت زرین‌پال sandbox.
- `npm audit`/OSV یا تولید SBOM بر اساس lockfile قابل‌بازتولید.
- SAST، DAST با ZAP، آزمون TLS/headers روی دامنهٔ زنده، یا آزمون نفوذ فعال.
- تست کامل BOLA/BFLA با چند حساب و نقش روی همهٔ endpointها.
- اتصال نهایی تمام صفحه‌های فرانت‌اند به API؛ برخی workflowهای قدیمی هنوز `localStorage` مصرف می‌کنند.

## موانع انتشار (باید پیش از production بسته شوند)

1. اتصال فرم‌های کامل ایجاد/ویرایش آگهی، صفحهٔ اصلی، علاقه‌مندی‌ها، پروفایل/نمایشگاه و پرسش‌وپاسخ به API و تعیین منبع واحد حقیقت در دیتابیس.
2. پیکربندی HTTPS و reverse proxy same-origin، secrets واقعی و مجزا، کلید پیامک و پذیرندهٔ درگاه، محیط sandbox و سپس تست پرداخت واقعی کنترل‌شده.
3. نصب dependencyها و ایجاد `package-lock.json`، اجرای audit وابستگی‌ها، SAST/DAST و رفع یافته‌ها.
4. آزمون منفی با حداقل دو کاربر و نقش‌های moderator/admin؛ تأیید اینکه هیچ کاربر نتواند آگهی، پیام، پیشنهاد، تصویر، سفارش یا دادهٔ حساب دیگری را بخواند/تغییر دهد.
5. backup/restore drill، پایش نرخ خطا و درخواست‌ها، سیاست نگه‌داری اطلاعات/لاگ، و بررسی الزامات حقوقی و حریم خصوصی.

**نتیجه:** این نسخه نسبت به نسخهٔ نمایشی قبلی مرزهای امنیتی مهمی اضافه می‌کند و ۲۵ تست محلی موفق دارد؛ اما این تست‌ها تست نفوذ یا تست یکپارچهٔ سرویس نیستند و برای ادعای «بدون نقص امنیتی» یا رفتن مستقیم به production کافی نیست. دفتر یافته‌ها، مدل تهدید، دامنهٔ آزمون و برنامهٔ اصلاحات در پوشهٔ `security/` ثبت شده‌اند. انتشار عمومی باید بعد از بستن موانع بالا و retest مستقل انجام شود.
