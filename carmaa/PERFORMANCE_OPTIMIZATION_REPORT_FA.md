# گزارش بهینه‌سازی عملکرد CarMaa

تاریخ بررسی: ۲۳ اکتبر ۲۰۲۶

## خلاصه

این پروژه فرانت‌اند استاتیک مبتنی بر HTML/CSS و JavaScript معمولی با بارگذاری ترتیبی فایل‌های سراسری است؛ بک‌اند با Node.js/Express کار می‌کند و از PostgreSQL، Redis، Docker Compose و Caddy استفاده می‌کند. در بک‌اند، پردازش تصویر با Sharp از قبل پیاده‌سازی شده بود. به دلیل معماری اسکریپت‌های سراسری، تغییرات تهاجمی مانند جابه‌جایی یا تقسیم گسترده‌ی فایل‌ها انجام نشد تا ترتیب وابستگی‌ها و قابلیت‌های موجود نشکند.

## علت‌های مشخص‌شده در کد

1. **شروع برنامه منتظر درخواست‌های مستقل به‌صورت ترتیبی می‌ماند.** همگام‌سازی آگهی‌های عمومی و فهرست نمایشگاه‌ها، و سپس خواندن آگهی‌ها/علاقه‌مندی‌ها/نمایشگاه متعلق به کاربر، می‌توانست زمان شروع را با جمع‌شدن تأخیر شبکه‌ها افزایش دهد.
2. **کتابخانه‌ی نقشه در مسیر اولیه بارگیری می‌شد، حتی وقتی صفحه به نقشه نیاز نداشت.** این مورد دو درخواست استاتیک خارجی (JavaScript و CSS مربوط به Leaflet) به مسیر بارگذاری اولیه اضافه می‌کرد.
3. **استایل فونت Fredoka در مسیر رندر مسدودکننده قرار داشت.** فونت فقط برای نوشته‌ی برند لازم است و نباید جلوی رندر محتوای اصلی را بگیرد.
4. **فایل‌های CSS و JavaScript کش مؤثر و محدودی در مرورگر داشتند.** HTML باید قابل بازاعتبارسنجی باقی بماند، ولی کد ثابت فرانت‌اند می‌تواند کش کوتاه و محدود داشته باشد؛ از کش immutable استفاده نشد چون همه‌ی URLها هش محتوا ندارند.
5. **تاریخچه‌ی جابه‌جایی رتبه‌ی نمایشگاه‌ها به‌ازای هر نمایشگاه و هر نوع رتبه‌بندی، دستورات نوشتن جداگانه اجرا می‌کرد.** این الگو تعداد رفت‌وبرگشت‌های دیتابیس را بالا می‌برد؛ نوشتن‌ها به کوئری‌های batch تبدیل شد.

## تغییرات پیاده‌سازی‌شده

- `js/41-api-bootstrap.js`: همگام‌سازی خواندنی آگهی‌ها و نمایشگاه‌های عمومی و نیز خواندن داده‌های مستقل کاربر با `Promise.allSettled` موازی شده است. اگر یک خواندن ناموفق باشد، خطاهای مستقل مسیرهای دیگر را متوقف نمی‌کند؛ ترتیب احراز هویت قبل از خواندن داده‌های خصوصی حفظ شده است.
- `js/00-leaflet-loader.js` (جدید): بارگیری تنبل Leaflet با تلاش برای دو CDN، جلوگیری از درخواست تکراری هم‌زمان و بازگرداندن وضعیت موفق/ناموفق.
- `index.html`: ارجاع مستقیم و زودهنگام به Leaflet حذف و loader محلی اضافه شده است. دانلود CSS فونت Fredoka به روش غیرمسدودکننده تغییر کرده و fallback برای غیرفعال بودن JavaScript افزوده شده است.
- `index_offline.html`: بارگیری فونت Fredoka با همان روش غیرمسدودکننده همسان شده است.
- `js/04-state-core.js`: نقشه‌ی جزئیات خودرو فقط هنگام رندرشدن بخش نقشه، Leaflet را درخواست می‌کند و پس از برگشت نتیجه بررسی می‌کند که slot هنوز متصل و route همان خودرو باشد.
- `js/14-pages-sell-saved-manage.js`: نقشه‌ی انتخاب موقعیت در فرم ثبت آگهی Leaflet را در صورت نیاز بارگیری می‌کند؛ وضعیت آماده‌سازی و fallback قبلی نگه داشته شده است.
- `backend/src/routes/showrooms.js`: درج و به‌روزرسانی تاریخچه‌ی رتبه برای هر sort به نوشتن‌های batch مبتنی بر آرایه و `unnest` تبدیل شده است؛ منطق مقایسه رتبه، قفل تراکنش، کش موجود و حذف snapshotهای نمایشگاه‌های حذف‌شده حفظ شده‌اند.
- `deploy/Caddyfile`: برای فایل‌های CSS/JS/JSON/webmanifest هدر کش کوتاه `max-age=300, must-revalidate` تنظیم شده است. HTML همچنان `no-cache` می‌ماند و فایل‌های رسانه‌ای از سیاست یک‌روزه‌ی قبلی استفاده می‌کنند. فشرده‌سازی gzip/zstd از قبل فعال بود و دست‌نخورده نگه داشته شده است.
- `backend/test/security-core.test.js`: تست عملکرد موازی‌سازی startup و نوشتن batch افزوده شده است؛ تست‌های قبلی و ادعاهای مربوط به حریم خصوصی/idempotency با رفتار واقعی کد هم‌تراز شده‌اند، بدون غیرفعال‌کردن تست‌ها.
- `deploy.sh` و `README_DEPLOY_FA.md`: نسخه‌ی دارای بازیابی/بررسی DNS از اصلاحیه‌ی قبلی حفظ شده تا نسخه‌ی بهینه‌شده آن اصلاح قبلی را پس نگیرد.

## اندازه‌گیری فایل‌های محلی

این ارقام از فایل‌های محلی و ارجاع‌های موجود در `index.html` محاسبه شده‌اند؛ **اندازه‌گیری مرورگر، درخواست‌های واقعی شبکه یا نتیجه‌ی Lighthouse نیستند**:

- ۵۰ مرجع فایل JavaScript محلی: حدود 1,389,342 بایت خام؛ مجموع فشرده‌سازی مستقل فایل‌ها با gzip حدود 470,961 بایت.
- ۲۱ مرجع فایل CSS محلی: حدود 1,085,387 بایت خام؛ مجموع فشرده‌سازی مستقل فایل‌ها با gzip حدود 222,907 بایت.
- ۱۲۸ فایل رسانه‌ای در فرمت‌های بررسی‌شده، مجموعاً حدود 4,719,785 بایت در کل پوشه‌ی پروژه.

مجموع gzip، فشرده‌سازی مستقل هر فایل است و سربار HTTP، کش مرورگر، پاسخ CDN یا فشرده‌سازی واقعی سرور را مدل نمی‌کند. اعداد قبل و بعد برای مرورگر به دست نیامده‌اند، بنابراین کاهش درصدی حجم انتقال یا زمان بارگذاری ادعا نمی‌شود. بهینه‌سازی تنبل نقشه تعداد درخواست‌های خارجی شروع صفحه را از دو مورد به صفر می‌رساند؛ این دو درخواست فقط وقتی مسیر نقشه نیاز پیدا کند انجام می‌شوند.

## اعتبارسنجی انجام‌شده

- `backend npm run check`: موفق.
- `backend npm test`: **۴۴ تست از ۴۴ تست موفق**، بدون تست ردشده یا غیرفعال‌شده.
- `node --check` روی فایل‌های JavaScript فرانت‌اند، `admin.js` و فایل‌های بک‌اند: موفق.
- `bash -n deploy.sh`: موفق.
- بررسی ایستا برای بارگیری تنبل Leaflet و سیاست کش فرانت‌اند: تست خودکار اضافه و پاس شد.

## مواردی که هنوز اندازه‌گیری/تأیید نشده‌اند

- اجرای کامل Build ایمیج‌ها: ابزار Docker در محیط بررسی در دسترس نبود؛ بنابراین Build واقعی Docker/Compose اجرا نشده است.
- اجرای end-to-end در Chromium: راه‌اندازی Chromium headless در این محیط حتی برای سروکردن صفحه‌ی ساده به پایان نمی‌رسید؛ بنابراین مسیرهای UI به‌صورت واقعی در مرورگر تست نشده‌اند.
- PostgreSQL/Redis زنده در دسترس نبودند؛ کوئری `EXPLAIN ANALYZE`، زمان واقعی endpointها، اندازه‌ی واقعی داده و مصرف RAM/CPU سرویس‌ها انجام نشده‌اند.
- LCP، INP، CLS، TTFB، تعداد واقعی درخواست‌ها و waterfall شبکه در گوشی یا دسکتاپ قبل/بعد اندازه‌گیری نشده‌اند.
- ایندکس دیتابیس جدیدی ساخته نشده است؛ بدون plan و حجم داده‌ی واقعی، افزودن ایندکس می‌توانست هزینه‌ی نوشتن و نگهداری غیرضروری ایجاد کند.

## انتشار امن

1. ابتدا از فایل‌های فعلی نسخه‌ی پشتیبان بگیرید و فایل‌های نسخه‌ی بهینه‌شده را جایگزین کنید.
2. دیپلوی را با روند معمول پروژه اجرا کنید و لاگ مراحل build/migration را بررسی کنید.
3. Volume دیتابیس، رسانه‌ها یا Redis را حذف نکنید؛ برای این بهینه‌سازی هیچ حذف داده یا migration تخریبی لازم نیست.
4. پس از انتشار، روی محیط staging یا تولید با ابزارهایی مثل Lighthouse/WebPageTest و با حساب کاربری آزمایشی، زمان شروع، صفحات آگهی/نمایشگاه/نقشه، ورود، علاقه‌مندی‌ها و ثبت آگهی را اندازه بگیرید. نتایج باید قبل/بعد با دستگاه و شبکه‌ی یکسان مقایسه شوند.


## بهینه‌سازی عملکرد — ۳ نوامبر ۲۰۲۶

### تغییرات نسخه‌ی فعلی
- تمام اسکریپت‌های اصلی با `defer` بارگیری می‌شوند؛ ترتیب وابستگی فایل‌ها حفظ شده تا parse کردن HTML پشت دانلود و اجرای تک‌تک اسکریپت‌ها متوقف نشود.
- ۴۴ فایل CSS محلی با حفظ ترتیب cascade به دو bundle فشرده تبدیل شدند؛ لایه‌ی نهایی عملکردی نیز بعد از تمام استایل‌ها قرار گرفت. دو بخش inline CSS در جای قبلی خود باقی مانده‌اند تا اولویت استایل‌ها جابه‌جا نشود.
- تعداد ارجاع‌های محلی اولیه از ۴۴ CSS و ۶۸ JavaScript به ۳ CSS و ۶۷ JavaScript رسید؛ یعنی ۴۲ درخواست محلی کمتر. اسکریپت‌های باقی‌مانده همگی `defer` هستند و ترتیب اجرای کلاسیک آن‌ها حفظ شده است.
- ابزارهای فقط-ادمین (`layout-editor.js` و `color-tool.js`) دیگر برای بازدیدکننده‌ی عادی دانلود نمی‌شوند؛ با `?layout=1` / `?colors=1` یا فلگ ذخیره‌شده همچنان فعال می‌شوند.
- زمان polling fallback اعلان پیام از ۷ ثانیه به ۲۰ ثانیه و polling مکالمه‌ی باز از ۶ به ۱۰ ثانیه افزایش یافت؛ رویدادهای SSE همچنان به‌روزرسانی فوری را انجام می‌دهند.
- به‌روزرسانی اعلان‌ها از هر ۲٫۵ ثانیه به هر ۱۵ ثانیه محدود شد و بازسازی بی‌دلیل DOM پنل اعلان‌ها از حلقه‌ی دوره‌ای حذف شد؛ رویدادهای SSE، storage و اعمال کاربر همچنان پنل را به‌روز می‌کنند.
- بررسی وضعیت اتصال SSE از هر ۳ ثانیه به هر ۱۵ ثانیه کاهش یافت؛ هنگام بازگشت به تب، وضعیت احراز هویت نیز دوباره بررسی می‌شود.
- افکت بلور سطوح بزرگ چسبان در موبایل به ۸px محدود شد؛ بلورهای کوچک و افکت‌های تعاملی حفظ شده‌اند.
- پنج تصویر فعال بنر/تبلیغ صفحه‌ی اصلی با حداکثر عرض ۱۴۴۰ پیکسل و WebP کیفیت ۸۲ بهینه شدند؛ ابعاد و نسبت تصویر حفظ شده و برای URLهای جدید نسخه‌ی cache-busting اضافه شد.

### اعتبارسنجی
- CSS هر دو bundle با tinycss2 تجزیه شد و خطای parse گزارش نشد؛ تعداد بلوک‌های سطح بالا و محتوای رشته‌ها نیز بین منبع و bundle بررسی شد.
- `node --check` برای تمام فایل‌های JavaScript فرانت‌اند و فایل‌های اصلی ابزار ادمین موفق بود.
- `npm --prefix backend run check` موفق بود.
- دو assertion قدیمی در `backend/test/security-core.test.js` با قالب فعلی همسان شد تا escape شدن `listingDisplayTitle` را بررسی کند؛ تست مربوطه موفق است.
- مجموعه‌ی کامل بک‌اند: **۴۸ تست از ۴۹ تست موفق**. تست باقی‌مانده در محیط فعلی به‌دلیل نصب‌نبودن بسته‌ی `pg` اجرا نمی‌شود (`ERR_MODULE_NOT_FOUND`)؛ این بسته در `backend/package.json` تعریف شده و پس از نصب وابستگی‌های بک‌اند باید دوباره اجرا شود.
- بررسی ایستای ترتیب scriptها، وجود تمام فایل‌های ارجاع‌شده، تعداد stylesheetها و مسیرهای محلی `url(...)` انجام شد.
- **اندازه‌گیری Lighthouse، LCP/INP، FPS یا تست روی گوشی واقعی در این محیط انجام نشده است**؛ بنابراین درصد بهبود زمان واقعی دستگاه ادعا نمی‌شود.
- نسخه‌ی اصلی فایل‌های تغییرکرده برای بازگشت، در پوشه‌ی جداگانه‌ی `carmaa-performance-restore/` کنار پوشه‌ی پروژه در ZIP قرار دارد؛ این پوشه را روی ریشه‌ی قابل‌سرو سایت کپی نکنید.
